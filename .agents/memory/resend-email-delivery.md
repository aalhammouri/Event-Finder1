---
name: Resend email delivery
description: Why Event Finder emails (activation/reset/digest) may silently fail to deliver, and the in-app fallbacks that prevent lockouts
---
- **Lockout-proofing:** because email delivery is unreliable (see below), admin routes also return activation/reset URLs directly so links can be shared out-of-band, and the zero-admin lockout self-heals — see [Admin lockout recovery](admin-lockout-recovery.md). Last-admin demote/delete is blocked (400) so you can't re-create the lockout.
- Emails go out via `connectors.proxy("resend", "/emails", ...)` in emailService.ts. The proxy injects the api_key automatically; the `from` address is controlled by our code.
- **Hard blocker for delivery: Resend has NO verified domain** (GET /domains via proxy returns an empty list). With no verified domain, Resend rejects any send except from `onboarding@resend.dev`, and that test sender only delivers to the Resend account owner's own signup email. So activation/reset/digest emails to normal recipients are rejected until a domain is verified.
- **Temporary fix in place:** `FROM_ADDRESS` defaults to `"Event Finder <onboarding@resend.dev>"` and is overridable via the `RESEND_FROM_EMAIL` env var. Once a domain is verified at resend.com/domains, set `RESEND_FROM_EMAIL` to a sender on that domain to deliver to any recipient — no code change needed.
- **The server-side `@replit/connectors-sdk` does NOT expose credential values.** `listConnections()` returns only schema/metadata (no settings, no from_email, no api_key); `expand:['credentials'|'settings']` → 400. Only the code_execution sandbox's privileged `listConnections('resend')` helper returns `settings.from_email`. To use a configured from address at server runtime, pass it via env var — don't try to read it from the SDK.
- **forgot-password only emails registered + activated accounts** and always returns the same generic 200 either way (account-enumeration protection). A fast (~20ms) 200 with NO "Password reset email sent"/"Failed to send" log line means the entered email matched no activated account, so no send was attempted.
- **Owner-detection trick:** while sending from `onboarding@resend.dev` (no verified domain), Resend returns 403 for ANY recipient except the account owner's own signup email. So a *successful* "email sent" log for recipient X (no error thrown, ~hundreds of ms round-trip) is proof that X IS the Resend account owner's email — and that delivery to X specifically works. Use this to identify the owner address without needing dashboard access.
- **Published-app gotcha:** prod launches with its own fresh DB; seeded/invited accounts there are typically *pending* (not activated), so reset is a silent no-op in prod even when it works in dev. Fix is first-time **activation** (Request access → /auth/register refreshes token + emails activation link), not reset. Prod DB is read-only via executeSql, so you cannot flip activated_at/role from here — the user must activate through the app, and role/admin changes need a code change + republish.
- **Weekly digest fragility:** its try/catch wraps the whole recipient loop, so one non-deliverable recipient throws and aborts the rest. Pre-existing; worth per-recipient handling if digest reliability matters.
- **Why:** transactional email requires domain verification (DNS records) before a provider will deliver from your domain — a user/infra action that cannot be done from code.
- **How to apply:** when "email not received" is reported, first confirm the recipient is an activated account, then check `GET /domains` for a verified domain. Don't promise delivery to arbitrary recipients until a domain is verified and `from` uses that verified domain.
