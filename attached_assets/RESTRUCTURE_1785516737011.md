# Extraction Pipeline Restructure — 2026-07-31

Rebuilds the crawl/extract path so an automated run recovers the same events a
careful manual scan of the same 87 sites found. Route handlers, the database
schema and the frontend contract are unchanged — this is a restructure of the
`services/` layer only.

---

## Why the old pipeline under-reported

A manual scan of the 87-site list found 37 upcoming events. The pipeline as
shipped would have discarded most of them, for four independent reasons:

1. **The avoid list was an unconditional veto.** Defaults were
   `["bingo", "walk", "wine", "arts", …]`, matched as plain substrings, and
   overridable only by the literal phrase "silent auction". That deleted
   Catholic Charities' **Wine** & Dine (Nov 13, auctions), MCC Foundation's
   **Wine** Dinner & Auction, Avondale House's **Bingo** Bash, Santa Fe's Purse
   **Bingo**, and every page of the Pearl Fincher Museum of Fine **Arts** —
   because "arts" appears in that organisation's own name.

2. **The AI was asked to judge whether an event had already happened, without
   being told today's date.** Both prompts carried "FUTURE EVENTS ONLY … return
   relevant=false", so `gpt-4o-mini` answered from its training cutoff. Events
   judged past were dropped before scoring or storage — not hidden in the UI,
   gone. Observed rate during the manual scan: 6 of the strongest finds
   (Boo Ball, the Sanctuary Gala, Cy-Hope's gala, Denim & Diamonds, Evening of
   Heritage, the Tapestry Gala) were all wrongly labelled past.

3. **Ticketing platforms were unreachable.** BFS follows same-domain links only,
   and platforms like GiveButter/OneCause were in the seed blacklist. But for
   these organisations the date, venue, ticket price and sponsorship ladder live
   on exactly those pages. That is why extracted events came back as a name with
   every other field null.

4. **Early exit fired before `/events` was reached.** `consecutiveNoKeywords >= 3
   && visited.size <= 5` abandons a site after five pages — and a nonprofit
   homepage almost always opens with mission/about/donate pages carrying no
   fundraising keywords.

## New modules

| File | Responsibility |
|---|---|
| `services/dates.ts` | All date reasoning. Parses the formats nonprofit sites actually publish, decides `isPast` and `weeksAway` in code, and supplies `todayForPrompt()` for prompt grounding. |
| `services/gate.ts` | Keyword gate. Strong/weak signal tiers; the avoid list is now a tie-breaker for weak pages, never a veto over hard fundraising evidence. |
| `services/ticketPlatforms.ts` | Registry of ~35 ticketing/auction hosts. Distinguishes "blocked as a seed domain" from "worth one hop as an enrichment target". |
| `services/enrichment.ts` | Follows one ticket-platform link per event and fills gaps (date, venue, ticket price, table price, auction flags, contacts). Values from the org's own page always win. |

## Rewired

- **`extractor.ts`** — both prompts now open with today's real date; the
  "FUTURE EVENTS ONLY → relevant=false" instruction is replaced with "copy the
  date as printed, do not judge whether it has passed"; recap-detection is now
  based on past-tense recap language, not on the date. Prompts are built per
  call (a module constant would freeze "today" at boot on a long-running VM).
  The old inline gate is deleted and re-exported from `gate.ts`.
- **`crawler.ts`** — calls enrichment after extraction; early exit can no longer
  fire while an event-path URL is queued; `isPast` recomputed via `dates.ts`;
  BFS/Firecrawl now report every processed URL so coverage is honest; the
  double-crawl fallback triggers on *zero pages crawled* rather than *zero
  events found*.
- **`scorer.ts`** — `isEventPast` and `computeTimingScore` delegate to
  `dates.ts`, so the scorer, crawler and events API can never disagree.
- **`dashboard.ts` / `emailService.ts`** — tier names normalised, so "Tier A"
  (current scorer output) and "A" (legacy rows) count together. The digest
  previously rendered zero events in both sections while its header claimed a
  count; it also gained an "Other Qualifying Events" section so nothing is
  silently omitted.
- **`crawlRuns.ts`** — `tiers` and `geographicStates` are shape-guarded, not
  just null-guarded.
- **`adminSettings.ts`** — `avoidKeywords` now defaults to `[]`;
  `geographicStates` now defaults to `[]` (no filtering).

## Verification performed

`services/dates.ts` parsing rules were executed against the exact date strings
collected during the manual scan: **24/24 cases pass**, covering
`"October 3, 2026"`, `"Saturday, October 3, 2026"`, `"Sat, November 14 2026"`,
`"2026-08-15T16:00:00-05:00"`, `"Dec 7, 2026"`, `"10/3/26"`,
`"September 4-5, 2026"` (range → first day), bare `"October 3"` (year inferred
forward), same-day (must NOT be past), and unparseable input (must NOT hide the
event).

The six events the old pipeline discarded now land in the scoring window they
deserve:

```
September 19, 2026  ->  7.1w  PRIME +25
October 3, 2026     ->  9.1w  PRIME +25
October 10, 2026    -> 10.1w  PRIME +25
October 23, 2026    -> 12.0w  PRIME +25
November 14, 2026   -> 15.1w  GOOD +10
December 7, 2026    -> 18.4w  neutral 0
```

## Deploy steps

1. `pnpm install`
2. `pnpm --filter @workspace/db run push` — schema defaults changed only; no new
   columns. Existing rows keep their stored values, so also run the two
   statements below to clear the harmful defaults already persisted:
   ```sql
   UPDATE admin_settings SET avoid_keywords = '{}';
   UPDATE admin_settings SET geographic_states = '{}';
   UPDATE events SET tier = 'Tier ' || tier WHERE tier IN ('A','B','C');
   ```
3. `pnpm run typecheck && pnpm run build`
4. Restart, then run one small URL list and confirm in the logs:
   - `"Event enriched from ticket-platform page"` appears at least once
   - no site is crawled twice after a successful Firecrawl pass
   - per-site coverage shows `isComplete: true` with plausible `pagesMissed`

| `ENRICH_MAX_CONCURRENCY` | 4 | Parallel ticket-platform enrichment fetches |
| `AI_MAX_CONCURRENCY` | 4 | Existing — parallel OpenAI calls |

## Cost note

Enrichment adds at most one extra fetch plus one `gpt-4o-mini` call per
*extracted event* (not per page), and only when a date, venue or price is
actually missing. That is a small increase against a large decrease: fixing the
double-crawl bug removes a full redundant BFS pass on every site that yields no
events — which is most sites.
